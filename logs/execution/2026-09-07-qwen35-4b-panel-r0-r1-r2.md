## 1. 捕获实现事故与修复（三次运行）

| # | 失败 | 根因 | 修复 |
|---|---|---|---|
| 1 | RoPE 设备错位 RuntimeError | qn/kn 先搬 CPU 而 cos/sin 留 GPU | RoPE 移到 CPU 重放（cos/sin 保 fp32） |
| 2 | 第 15/17 窗 raw `CUDA error: out of memory`（连 empty_cache 都失败，期间 nvidia-smi NVML 报错） | **GPU 仅 8GB < 4B fp16 模型 ~8GB**；前 15 窗由 Windows WDDM sysmem fallback 硬撑，必然崩 | 默认 `--device cpu`（bf16 前向）；hook 内即时落 CPU；序列化前先释放模型 |
| 2b | （②重写引入）hook 覆盖 bug | 所有 panel 层共用一组 hook key，单次全模型前向逐层互相覆盖——24 层会全部读到最后一层的激活；若不 OOM 会落盘垃圾缓存 | per-index key（`f"{i}:..."`） |
| 3 | load_pack 拦下 `calibration_activations[q][0][0] is not a 2-D tensor` | hook 重构后 `_flat16` 漏套，激活保留 [1,seq,width] 3-D | run_window 补 `_flat16`；校验器按预期工作 |

- 4B 面板只提供**同族结构机制鲁棒性/失败模式**证据，不提供官方分数预测能力；

## 6. 构成修正（19:25–20:05，用户质疑「linear太多、attention太少」后）

- 质疑有效性：官方构成为 50 Linear + 250 Attention（attention 主导 5:1）；初版 4B 面板
  336:12（28:1）的 attention 侧过薄——根因是沿用了 0.5B v3 的 compact-pair 政策
  （每 shard 2 窗），0.5B 有 24 层全 FA（48 例）而 4B 仅 6 层 FA（12 例）。
- 修正（三处代码 + 重抓）：
  1. `capture_qwen35.py`：test Q/K/V 改存**全部 12 个测试窗**（+330MB，总 6.28 GiB），
     线性测试激活仍只存 {1,2,6,7}；metadata/sidecar 增 `test_qkv_windows`。
  2. `official_eval.load_pack`：test_qkv 校验槽位改读 `test_qkv_windows`
     （旧 pack 回退 `test_activation_windows`）。
  3. `proxy_v3_eval.prepare_shard`：heterogeneous 面板 attention 场景用全部已存 QKV 窗
     （legacy 保持 compact-pair 轮转）；`eval_system._panel_geometry` 增
     `attention_windows` 计数并接入 coverage 期望。
- 重验（cache `qwen3.5-4b-proxy-v2.pt` v2，6.28 GiB，19m51s CPU）：
  - R0：72/72 FA QKV 槽位全有限、2-D；sidecar/metadata 一致。
  - 全六 shard 基线（`qwen35-4b-baseline-v189-attn72`，9m32s，校准缓存全命中）：
    **Linear 336c mean 0.524265（与修正前逐位一致——确定性验证）
    / Attention 72c mean 0.526517，median 0.544639，min 0.228 / max 0.818**
    （旧 2 窗政策下 attention 分布尾部被低估：min 0.280 / max 0.734）。
    overall 0.524663；六 API 调用 W 0 / A 336 / A_calib 0 / QKV 72/72/72。
- 结论：两侧 case 数现在是 336:72（4.7:1），attention 侧超过 0.5B eval-v3 的 48 例；
  DeltaNet 不能进 attention 场景是官方 Q/K/V API 合同的结构约束（非设计遗漏），
  Linear 含 DeltaNet in_proj/out_proj 与官方权重族一致。

## 7. 全面 4B 化：0.5B 面板退役（20:16，用户指令）

- 用户指令：「不要用0.5B的，全部使用4B进行测试」。机制判读此前已在 4B；
  本次变更把 **0.5B fresh default 时间门**也退役，全部测试（机制+时间）只跑 4B。
- **技术要点**：0.5B 时间公式系数不可代入 4B 秒数——v189 4B 实测
  （W 697.1 / A_calib 15.0 / dyn_act 279.2 / qkv 0.8）代入得 ~465s vs 官方 275s，
  自证失效。取代方案：**4B paired Δ 时间门**——
  `预测 = 父官方时间 + ΣΔ（候选 fresh 六 API 秒 − 父 4B 锚点六 API 秒）`，<280s 提交。
  Δ 1:1 传递是显式假设（无 4B↔官方时间配对）；每次官方回传登记残差，积累后评估重拟合。
- **v189 4B 时间锚点登记**（fresh 全量 run，22m10s 那次，校准实际执行）：
  api_total **992.1s**（W 697.1 / A_calib 15.0 / dyn_act 279.2 / qkv 0.4+0.2+0.2）。
  注意 attn72 重跑（272s）是缓存命中，**不可作计时锚点**。
- 计时纪律：主 run 必须 fresh（校准实际执行），同一 run 兼产机制统计与计时行；
  缓存命中 run 的 api_seconds 不可当计时行；计时前确认 GPU 空闲（gpu.lock）。
- 预算提示：v189 官方 275s → 根父候选 Δ 预算仅 +5s（280s 门）；时间敏感改动
  优先挂 anchor22-a2（271s，预算 +9s）等余量更大的父。
