# v190 官方 TIMEOUT 的后果与对后续方向的影响（2026-09-08）

> 官方结果的正式登记见
> [`2026-09-08-attn-diag-reciprocal-balance.md`](2026-09-08-attn-diag-reciprocal-balance.md)
> （状态 `TIMEOUT`、分数 NA、时间 `>300s`、用户回传）与归档 `result.md` / `config.json`。
> 本文件只登记**后果、判读和下一步约束**，不重复身份与配置。

## 1. 裁决

- TIMEOUT 按流程**只关闭这一个实现**（v190 的校准 + 门控 + 编译路径），不做 fit/gate 窗口、
  token 数、chunk、clamp 范围的邻域重试。
- 该方向**没有官方正向、也没有官方负向数据点**：超时不给分，不能判定"逐通道 Q/K 互逆平衡"
  机制无效。
- 根不变：`12352EFD…E24E`（18032 / 280s）。

## 2. 两个必须记住的过程事实

1. **本地本就被自己的门控拒绝**：唯一测试层 `diag_attempted=1`、`diag_accepted=0`、
   `diag_arm=parent`；shard0 paired `0/0/12`、delta `0`。部署侧至多与父逐位相同，
   这次提交唯一确定的效果就是**新增校准耗时**。
2. **本地成本比值不能换算官方**：shard0 候选 API total `5.625367s` vs 父 `0.748119s`。
   按 AGENTS §6，校准缓存命中会把校准 API 的秒数与调用数记为 0，父子缓存状态未必一致，
   所以这个 7.5× 只能当作"候选确实新增了实质校准计算"的定性证据。

## 3. 对后续方向的影响（事实，不是新门禁）

- 方向一是四个 Attention 方向里**成本最低**的（一次统计 + 一次硬编码，无 32 步训练），
  仍然超时 ⇒ **根当前的 20s 余量装不下任何新增的 Attention 校准计算**。
- 已在队列中的两个候选成本都高于方向一：
  - `v191 attn-block-triangular-transport`（两次 64×64 SVD + 首次翻码步长搜索）；
  - `v192 attn-full-reciprocal-residual`（32 步 Adam + 矩阵指数，历史 A22-2/A23 侧隔离
    即为 271/276s 档位）。
  按方向一的实测，**二者在当前余量下超时风险更高**。
- 尤其 `v192` 与 v190 同一情形：本地 gate 拒绝、shard0 delta `0`（部署等于父），却带最高成本。
  按现状提交等于"父 + 惩罚时间"，信息收益为零。
- 与 [`2026-09-08-active-plan-review.md`](2026-09-08-active-plan-review.md) 的 F1/F2 一致，
  本次实测把判断进一步收紧：**先降时，再谈新机制**。

## 4. 建议（待用户决定是否写入计划）

1. 本地 `accepted=0` 且 shard0 delta 逐位为 0 的候选**不再直接提交官方**。若认为门控可能误判，
   应换门控窗口/参数化重做候选，而不是把同一个 rejected 提案送官方。
2. 在拿到 ≥40s 余量之前，v191/v192 不做官方提交；优先做降时卡（目标 ≥40s，解锁 R3→A2 的 +35）。
3. 若坚持提交 v192，至少先做一次成本裁剪（砍 driver 折数 / 减少 hard 前向次数 / 批处理），
   并在提交说明里写明"已知本地 gate 拒绝、预期收益为 0"这一风险。
