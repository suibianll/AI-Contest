# v98 官方超时（最新 300s 限制）

> 日期：2026-08-31  
> 官方反馈：用户确认 **v98 在官方最新规则下判为 timeout**。  
> 纠错说明：此前曾将 v107 误记为官方 timeout；用户确认 **v107 并非 timeout**，官方结果
> 仍是 Attention `wrong answer`（与 v100 同类）。真正在新限制下官方判为 timeout 的是
> v98（B1 GQRB margin 版）。  
> 官方评测（2026-08-31 再次修订）：端到端超时限制从 420s 收紧为 **`300s`（5 分钟）**，
> 且官方不再限制任何 `A@W` 拟合用法（`Q(W)`、`Q(A)` 均可自由使用），只限制总运行时间；
> 评测协议版本已升级为 v5。

## 判定

v98（v098 B1 GQRB margin 版）本地旧口径 Qwen API `406.24s`，已超过最新 `300s` 限制
（全量运行时间与其一致），因此官方结果类别为 **`timeout`**。官方未提供精确超时时间与分数。

- v98 不再作为提交候选；`Official Score/Time` 更新为 timeout / NA。
- 与 v98 同源的 B1 GQRB margin 机制（基准 top4 + GQRB top4）在本地仍有益，但任何新候选
  必须以端到端 `<300s` 为硬门，不能以 v98 的 `406.24s` 为基线。

## 对候选集合的影响

1. 后续候选必须以已官方通过的 v74（`22750 / 239.387s`）为 Attention 安全基线。
2. 新的 300s 限制 + 无 `A@W` 限制意味着：候选可自由用 `A@W` 优化 `Q(W)`/`Q(A)`，
   但端到端运行时间必须严格 `<300s`（最终以官方平台实测为准）。
