# 父激活路径拆分探针：一次定位，回答计划 §4 的分支选择

活动计划：`docs/superpowers/plans/2026-09-10-linear-correctness-and-runtime-plan.md` §4。
本目录**不是候选**，不分配版本号、不提交官方；它只回答一个问题并为 §4 选一张固定卡。

- 第一层探针：`split_probe.py`；结果 `split_probe.json` / `split_probe.out`
- 第二层探针：`encoder_probe.py`；结果 `encoder_probe.json` / `encoder_probe.out`
- 两个探针都只读，都不改动发布源码一个字节
- 父根：SHA256 `0f1af6dbc207ff32b2c6be16987e9c4fe50f3f10747de26782ef52a6f2fab7bc`（v230 Linear L-EM2 + v195 Attention）
- 设备：NVIDIA GeForce RTX 3060 Ti；15 轮取中位，3 轮预热，无 profiler

## 为什么开这个探针

L-TF1 的归因（`linear-tf1-gradient-reuse/attribute.py`）把一次动态调用切成三块：
父根自己的动态激活路径 **90.0% / 93.2%**（128 / 512 行）、L-EM2 的新增下降 10.0% / 6.8%、
度量构造与求逆 3.2% / 3.5%。那个 90–93% 是**一个整桶**，桶里同时装着
nvfp4 解码与 smooth/permute、块序选择、逐块 GPTQ 补偿求解、hook 与 state 拷贝。

计划 §4 的分支 2（"预计算原始块间的补偿系数，动态阶段按当前输入的块序取用"）
只在**逐块 solve 为主**时才成立。当时没有任何测量支持这个前提，
把整桶当成 solve 就是把猜测当定位。所以这里只开一个探针、只做一次拆分，不做参数/seed/阈值/粒度扫描。

## 方法

父根的三个助手（`_static_actorder_dense_from_state`、`_combined_dynamic_sample_energy_block_order_fast`、
`_combined_dynamic_fast_reordered_gptq`）都是**调用时从模块全局解析**的，所以在模块全局上换一个
直通 wrapper 就能测到真实发布路径，而不改动它的任何一个字节。wrapper 调用原函数并原样返回结果——
做了别的事就是在测另一个程序。

每段用一对 `torch.cuda.Event` 加一对 `perf_counter` 夹住，事件只在整轮 sync **之后**才读
（未完成的 event 读 `elapsed_time` 不是测量）。两种钟都记，因为它们回答不同问题：
event 是 GPU 流时间，`perf_counter` 是含 CPU 侧 Python 的墙钟。一个在墙钟上大、在事件钟上小的段
就是 CPU 受限的，这决定了分支 2 这种 GPU 侧重算能否碰到它。

内层拆分（`_dense_to_hif4` 与 `torch.linalg.solve`）是在**同一个探针**里加的一层括号，
不是第二个探针：第一次运行只显示 `gptq` 占 80–95%，而它同时含逐块编码器和补偿求解，
无法区分分支 2 与分支 3。

## 结果

**外层（占整次调用）：**

| 部件 | q 2560ch,128行 | q,512行 | o 4096ch,128行 | o,512行 |
|---|---:|---:|---:|---:|
| `full_ms` | 539.81 | 899.03 | 498.53 | 530.23 |
| `dense`（解码 + smooth + permute） | 0.756 (0.14%) | 0.804 (0.09%) | 0.801 (0.16%) | 0.965 (0.18%) |
| `order`（块序选择） | 0.243 (0.04%) | 0.237 (0.03%) | 0.233 (0.05%) | 0.257 (0.05%) |
| `gptq`（reordered GPTQ） | 504.013 (**93.4%**) | 851.169 (**94.7%**) | 428.928 (**86.0%**) | 424.827 (**80.1%**) |
| 残差（hook + state 拷贝 + CPU 空隙 + L-EM2 下降） | 34.799 (6.45%) | 46.821 (5.21%) | 68.568 (13.75%) | 104.186 (19.65%) |

**内层（在 `gptq` 内，括号内为占整次调用）：**

| 部件 | q,128行 | q,512行 | o,128行 | o,512行 |
|---|---:|---:|---:|---:|
| `encoder` = `_dense_to_hif4` | 471.981 (93.6% / **87.4%**) | 816.760 (96.0% / **90.8%**) | 374.855 (87.4% / **75.2%**) | 370.046 (87.1% / **69.8%**) |
| `solve` = `torch.linalg.solve` | 12.837 (2.55% / 2.38%) | 13.325 (1.57% / 1.48%) | 21.848 (5.09% / 4.38%) | 21.047 (4.95% / 3.97%) |
| gptq 其余 = gather + 补偿矩阵乘 | 19.195 (3.56%) | 21.084 (2.35%) | 32.225 (6.46%) | 33.734 (6.36%) |

两种钟在所有段上一致到 1% 以内（如 q/128 的 `encoder`：event 中位 11.631 ms/次、墙钟 11.590 ms/次），
所以这些段不是 CPU 受限的假象。

调用次数自我印证：`encoder` 每次调用 40 次（2560/64）与 64 次（4096/64）正是块数，
`solve` 39 与 63 次正是块数 − 1——补偿只在该处发生，没有跑到别的路径上去。这两条把括号放对了位置，
是探针自身的正确性检查。

## 结论

**分支 2 被实测排除。** 块间补偿系数的全部成本（`solve`）最多只占一次调用的 **2.4–4.4%**，
把它整体预计算到校准期，上限就是把这点拿掉。这不是本卡要的"秒级"。

**分支 3 被选中。** 主项是编码器 `_dense_to_hif4`，占一次调用 **69.8–90.8%**，
按 64 通道块被调用 40 / 64 次。

## 一个额外的实测事实：编码器成本与行数几乎无关

| 通道 | 每块 128 行 | 每块 512 行 |
|---|---:|---:|
| 2560（40 块） | 11.80 ms | 20.42 ms |
| 4096（64 块） | 5.86 ms | 5.78 ms |

4096 通道下 4 倍行数成本不变；2560 通道下按行数线性拟合得
**每块固定项 8.93 ms + 0.0224 ms/行**，即 128 行时 76% 的每块成本与行数无关。

这与"每块一次候选 scale 精确求解"的结构一致：`refine_cap = min(ceil(total_blocks * refine_ratio),
max_refine_blocks)` 被 `max_refine_blocks` 夹成一个与总块数、与行数都无关的常数，
于是 `_solve_exact_hierarchy` 在 `num_candidates` 个 scale 提议上的成本主要由逐块/逐候选的固定项决定。

所以下一张卡（§4.2）的目标是**逐块固定开销**，不是逐行算术，也不是补偿系数。

## 第二层：编码器内部（`encoder_probe.py`）

计划 §4.2 把最后一层定位问题写成"那 8.93 ms/块里，候选 scale 的精确求解占多少、其余张量搬运占多少"。
`encoder_probe.py` 就回答这个，方法同前：按名解析父根助手、在模块全局包一层直通 wrapper，
发布代码一个字节未改；CUDA event、`perf_counter`、`thread_time` 三钟齐读，15 轮取中位。

**先说一个必须先纠正的结构**：`_adaround_mantissa` 是**嵌在** `_solve_exact_hierarchy` 里面被调的
（`_solve_exact_hierarchy` 每个指数各调一次），所以两段的 event 区间是包含关系，
直接相减会出现负的"其余"。按调用次数还原：每编码器调用 `_adaround_mantissa` 共
1（`_dense_to_hif4` 直接调）+ 3（批量解）+ 3×边扩展次数 ≈ 9.18 次，实测 367/40 = 9.18 ✓，
其中只有直接那一次在解之外。下表已按此重算。

**每编码器调用（父根 layer0，CUDA event 中位；插桩使绝对值比 `split_probe.py` 高 2–8%）：**

| | q 2560ch/128行 | q/512行 | o 4096ch/128行 | o/512行 |
|---|---:|---:|---:|---:|
| 编码器 total | 12.750 ms | 20.911 ms | 5.956 ms | 6.087 ms |
| 候选精确解·批量（`[6,N,8,2,4]`，每调用 1 次） | 3.360 (26.4%) | 11.124 (53.2%) | 0.869 (14.6%) | 0.886 (14.6%) |
| 候选精确解·边扩展（4 维、逐步、每调用 ~1.7 次） | 4.602 (36.1%) | 4.636 (22.2%) | 1.253 (21.0%) | 1.290 (21.2%) |
| `_adaround_mantissa` 直接调用（每调用 1 次） | 0.711 (5.6%) | 1.548 (7.4%) | 0 | 0 |
| 其余（前导张量搬运） | 4.077 (32.0%) | 3.603 (17.2%) | 3.834 (64.4%) | 3.911 (64.2%) |
| 主线程 CPU 时间 / 墙钟 | 95% | 97% | 98% | 94–100% |

（上表的"批量解/边扩展"已含各自嵌套的 `_adaround_mantissa`；故 q 的
`_adaround_mantissa` 合计 6.525 ms = 12.750 的 **51.2%**，其中边扩展承担 56%、批量解 33%、直接调用 6%，
与调用次数分布一致。）

**候选数 K = 6**：`_offsets_as_tuple` 会把 `0` 前置进 5 个 offset，实测批量解输入形状
`[6, N, 8, 2, 4]`（q/128 的 N=128、q/512 的 N=509，即 `ceil(512×0.99366)`）——**refine 不是挑选，
`max_refine_ratio≈0.99`、`error_threshold=1e-7` 使几乎每一行都进 refine**。

**第三个钟回答了"这段是算力还是调度"**：主线程 CPU 时间占墙钟 94–100%，
即整个编码器窗口都在 CPU 侧付费，不是在等 GPU 算。

**aten 算子计数（`TorchDispatchMode`，仅计数、不在该模式下取任何时间）：**

| | q/128 | q/512 | o/128 | o/512 |
|---|---:|---:|---:|---:|
| 每编码器调用 aten 算子数 | 1060 | 1068 | **425** | **425** |
| 折算 µs/算子 | 11.8 | 19.6 | 14.0 | 14.0 |

两件事由此确定：

1. **算子数只随配置变、不随行数变**（o 的 128 行与 512 行算子数逐项相同，q 的 1060 与 1068 差在
   边界上的 `topk`/`index_select`）。这正是第一层看到的"每块成本与行数无关"的机制：
   成本是**发出的算子数 × 每个算子的固定代价**，不是浮点运算量。
   q 的 µs/算子从 11.8 涨到 19.6（算子数几乎不变、行数 4 倍）说明它多出来的部分是**数据量**驱动的（16 倍展开的中间张量），
   而 o 在两个行数下都是 14.0 µs/算子。
2. **gram 层与无 gram 层的热点不是同一个**：q（有 gram）走 `_adaround_mantissa` 的 16 模式枚举，
   占 51–76%；o（无 gram）根本不调它，"其余"前导搬运独占 64%。

**该优化哪一类，用真实调用点分布定，不用印象定**：父根 168 个 linear 动态调用点里，
2560 通道（有 gram）120 个、4096 通道（无 gram）24 个、9216 通道（无 gram，且不在 metric 作用域）24 个；
按通道宽度算 2560-gram 307200 对 4096-no-gram 98304，**gram 层约占动态激活宽度的 76%**。

**结论：分支 3 的热点确定为 gram 层编码器里 `_adaround_mantissa` 的 16 模式枚举**
（在 q/512 上是编码器的 68%，在 2560 通道层上占动态激活宽度的 76%），
它每次调用把 `[K,N,8,2,4]` 张成 16 倍并**以 int64 物化**，再转 float32、再乘回 mantissa——
这一段是可证明逐位等价的纯组织问题（见计划 §4.2）。

## 边界（这份结果不主张什么）

- 这些是**本地无 profiler 的相对分解**，不是官方秒数，不能换算官方时间；
  `full_ms` 只是本机这一次运行的整调用中位，跨进程不可与 §5.3 的 API 计时相加或相减。
- 探针只覆盖 layer0 的 `q`(2560) 与 `o`(4096) 两个真实 state、两种行数；没有扫层、没有扫 shard。
- 残差含 L-EM2 下降，与 `attribute.py` 的 10.0% / 6.8% 在运行间方差（约 15 ms，3%）内相容；
  本探针**不**重新定价下降，只负责把"父路径那一桶"拆开。
- 没有测到 `proj`（9216 通道）：它不在 metric 作用域内，不走这条路径，测它等于测一段本卡动不了的代码。
- 第二层的绝对值带插桩代价：`torch` 模块级包装与 dispatch mode 都会加开销，同配置下比
  `split_probe.py` 的**未插桩**读数高 2–8%（q/128 12.750 对 11.80、o/512 6.087 对 5.78）。
  两层的**比例**不受影响，绝对值不作跨脚本比较。
- aten 算子数是**计数**，不是时间归属：它只说明路径发了多少算子，不说明每个算子花了多少。
  µs/算子是由计数与 event 时间相除得到的**折算值**，不能反过来读成"某个算子耗时"。
- `_adaround_mantissa` 与 `_solve_exact_hierarchy` 是**共享助手**（权重/静态路径也在调，
  见 `solution.py` 的 1475/1970/7222/7258/7427/7463 等），本探针只统计调用点，不改任何一个。
  任何针对它们的改动都必须对全部调用者证明逐位等价，这条在 §4.2 卡里是硬线。
