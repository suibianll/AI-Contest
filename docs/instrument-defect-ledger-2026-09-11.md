# 分析仪器缺陷台账（截至 2026-09-11）

> 只记**我自己的分析仪器**（诊断脚本、测量脚本、验证脚本）的缺陷。
> 目的：让每一条纪律都能追到它对应的那次事故。**不含实现候选的 bug**。
> 早期 1–11 条在 `workbench/full_solution/attention-output080/report-080-verdict.md` §7；
> 本文合并 12–26 并与那一份对接。

## 一、失效模式分类

26 条里只有 **5 类**。分类比清单重要——因为**清单能逐条修，类别只能靠纪律防**。

| 类别 | 数量 | 是否会自己暴露 | 对应纪律（计划 §6） |
|---|---|---|---|
| **A. 代理 ≠ 目标**（拿一个量当另一个量的判据） | 6 | 否 | 判据必须与真实输出挂钩 |
| **B. 把中间产物当结论**（上界/最优/饱和的过度外推、判据口径错） | 5 | 否 | 不得由有限实验推整族 |
| **C. 仪器本身写错**（代数、索引、形状、类型、测错对象） | 9 | **部分会**（矛盾时） | 每卡带独立于下游效果的检查 |
| **D. 与被评测函数不一致**（重建了另一个函数） | 2 | **否** | §6.7 必须从 `evaluator/` 读源码 |
| **E. 运行环境**（并发覆盖、盲写补丁、用错解释器） | 4 | **否** | §6.6 本地运行不得并发 |

**关键：17 / 26 条属于"不会自己暴露"的类别。** 它们跑得出完全合理的数——
只是那些数不是你以为的那个量的数。这就是为什么"gate 拒收"永远不能当证据、
为什么每张卡必须带一个**与下游效果无关**的检查。

## 三、三条从事故直接长出来的纪律

1. **§6.7 为分析而重算的被评测函数必须从 `evaluator/` 读源码**（← #19）。
   重建评测器函数 = 在另一个函数上做线性化；读数会静默失真。
   注意 #19 的事故函数（带因果掩码的 attention）**本身完全合理**，跑得出完全合理的数——
   这正是它难以发现的原因。
2. **§6.6 本地运行不得并发**（← #17）。并发写出的是两个都"合理"的结果混在一起。
3. **每卡必须带独立于下游效果的检查**（← #13/#14/#16）。三条里没有一条会以"结果异常"的形式出现。

## 四、由 #21–#23、#26 长出的流程纪律

**先冒烟，再全量。** 诊断脚本必须支持在**几秒内跑单层/单 token**：

索引、形状、广播、dtype 四类错误全在第一次冒烟就暴露，不必等整跑。

**用 `.venv\Scripts\python.exe` 跑一切探针**（#26）。系统 `python` 是 CPU-only torch；
仓库的 CUDA 环境是 `.venv`。GPU 空闲时用 CPU 跑 = 自找的 10–30× 墙钟。

**不要用盲写 `str.replace` 改脚本**（#24）。补丁式修复在断言只检查"出现次数"时不检查"落点"，
会静默改错位置。**要么整篇重写，要么改后用搜索结果复核落点。**

## 五、一条诚实的自评

**小形状 control 卡**上。这个错误率说明：**我在这类探针上的实现可靠性不高**，
而探针的价值恰恰取决于它报的数可不可信。

因此本轮所有读数的**默认置信度应当是低的**，除非它带有与本结论无关的独立证据
（例如：互逆性由不变量检查证明、码可达性由计数证明、时间由调用计数证明）。
凡是没有独立证据的读数，一律标注"未独立核验"。

## 七、#37：编辑器写回时静默改写了行尾

**族**：实现缺陷（§五 同类），但**在"纯追加"纪律下才暴露**。

**经过**：v243（A-TF1）第一版用编辑工具改 `solution.py`。改动本身只有一处（把两行循环不变量
提到窗口循环外），但写回后 `diff` 报了一个 **713 行**的额外 hunk。逐字节定位后确认：
**文件尾部 713 行的行尾从 LF 变成了 CRLF**（父文件 `solution.py` 是**混合行尾**：
前 11852 行 CRLF，其后 LF）。编辑器按"文件的主体行尾"归一化了整篇。

**后果**：如果只跑等价性就归档，这一版仍然会通过（行尾不影响 Python 语义），但它已经不是
"父字节 + 单一 hunk"，而是附带重写了 713 行。仓库的 `cmp` 纯追加核验**会被它绕过**
（因为 `cmp` 只看前缀），而 `git diff` 会显示一个无法解释的巨型 hunk。

**修法**：用**字节级替换**重建 ——
`old` 片段在父字节里 `count() == 1` 断言唯一，替换后核验 `head identical` 与
`tail identical`。这是唯一能保证"区间外逐字节相同"的做法。

**长出的纪律（两条）**：

1. **改 `solution.py` 之后，必须跑 head/tail 逐字节核验，不能只看 `cmp` 前缀或行数。**
   `cmp` 前缀相同**不蕴含**"只有一个 hunk"。
2. **不要用编辑器直接改 `solution.py`**；用字节级替换脚本，并把
   `old` 片段的唯一性断言和 head/tail 核验写进同一个脚本。

**它为什么没自己暴露**：行尾差异对 Python 语义**完全不可见**，等价性检查也看不见它；
只有 `diff`/`git` 这类逐行工具才看得见，而当时的检查用的是 `cmp` 前缀。属"不会自己暴露"类。

## 八、#38：探针没有固定设备，量出的是一个**不对应任何真实配置**的混合路径

> **本节初稿写成"虚高 3.6 倍"，那是错的**，已改。真正的问题是**设备未被控制**，
> 而"虚高"这个说法暗示了唯一正确尺度，实际存在**两个都真实**的配置。

**族**：实现缺陷（计时口径），**且它污染了我此前每一张时间卡的绝对值**。

**经过**：A-TF1（v243）与 A-TG1（v244）的时间探针都这样构造输入：

```python
{r: v2._pair(pack["calibration_qkv"][s][layer][i].to(torch.float32)) for r in ("q","k","v")}
```

而评测器（`official_eval.py:2594`）是：

```python
_move_qkv(pack.calibration_qkv[sample][layer], device)   # _pair 后搬到算法设备
```

两个差别：**① 我多做了 `.to(torch.float32)`；② 我没有搬到 GPU。**

**① 无害**：实测 `_pair(float16)` 与 `_pair(float32)` 的 carrier/scale **逐元素相等**
（`max|diff| = 0.0`），所以输入数据是同一批，等价性结论不受影响。

**② 这才是问题**：张量留在**脚本自己的** device 上，而 `hif4_calibration_attention` 内部
**自己另选一次** device（`torch.device("cuda" if torch.cuda.is_available() else "cpu")`）。
于是同一次调用里，基准栈跟着输入跑在 **CPU**，训练器跟着内部选择跑在 **GPU**。

**实测同一层 `hif4_calibration_attention`：**

| 路径 | 单次耗时 |
|---|---|
| 输入留在 CPU（探针原样） | **16.3 s** ← 混合路径，不对应任何真实配置 |
| 输入搬到 GPU（`proxy_v3` 面板口径） | **4.53 s** |

面板 manifest 里**早就有** 4.53 s/次这个数（`20260911-vk-kernel-shared` 的 `api_seconds` ÷ `api_calls`），
**我没有去对**。一对就立刻发现 3.6 倍差距。

**后果（两次测量的相对量本身就随设备翻转，这是真正危险的地方）：**

| 机制 | GPU 路径 | CPU 张量路径 |
|---|---|---|
| A-TF1（v243）循环不变量外提 | **−6.17%** | −1.18% |
| A-TG1（v244）共享 standard 臂 | −1.03% | **−6.31%** |

两者**互补**：A-TF1 省 Python 分发（GPU 上占比大），A-TG1 省注意力前向（CPU 上占比大）。
所以"哪个更值钱"这个排序**在不同设备上会反过来**。原探针未固定设备，给出的排序
**既不是面板的，也不是官方的**。

**修法**：探针显式固定设备 —— `{r: tuple(t.to(dev) for t in v2._pair(...))}`，并在两条路径上都测。

**长出的纪律（三条）**：

1. **计时探针必须显式固定设备**，不能依赖被测函数内部自己选。
   本例中"数据一样"和"设备一样"是两件事：数据确实一样（`_pair(f16)` 与 `_pair(f32)` 的
   carrier 逐元素相等，`max|diff|=0.0`），**只有设备这一半有害**。
2. **"可分辨于噪声底"只证明测量精度够，不证明被测对象对。** 还要加一条：
   **测到的绝对量级必须与仓库里已有的外部读数对得上**。有现成读数可比而没比，读数不算数。
3. **设备之间的相对量不可默认迁移**（本机 GPU ↔ 官方鲲鹏 CPU）。报告必须写明是哪条路径。

**影响范围（要如实记）**：v243 / v244 的**等价性结论不受影响**（候选与父在同一路径上比，
逐字节相同，且在 GPU 与 CPU 两条路径上都验过）。受影响的是**时间数值的口径标注**。

## 九、#39：冗余签名只覆盖了一半入参

**族**：推理缺陷（差一点据此改代码）。**没有造成错误改动**，但结论当时已经写进卡片。

**经过**：A-TR1（v245）的定位手段是给 `_attention_deployed_mse` 的每次调用做签名，
找"重算已算过的"调用。签名是：

```python
rec.append((sys._getframe(1).f_lineno, sig(qs), sig(ks)))
```

**只哈希了 `(q_state, k_state)`**，其余入参
（`a1_q_pairs, a1_k_pairs, a1_v_hats, refs, q_head/kv_head/head_dim`）**完全没进签名**。

据此我在卡片里写下"第二个冗余点：lines `[10217, 10647]` 是同一状态对，算了两次"。
**核对代码后不成立**：10217 传**全量** `a1_q_pairs`，10647 传 **`validation_*` 子集**
（由 `validation_indices` 取出）。参数不同 ⇒ 结果不同 ⇒ 不是重复。

**为什么本卡真正的改动没受影响**：line 10513 的 13 次调用**全部来自同一行**，
入参逐字相同，只有 rotation state 不同。所以那一处的判定是成立的。

**长出的纪律（一条，但很关键）**：

> **冗余签名必须覆盖函数的完整入参。** 只覆盖一部分时，"签名相同"既可能来自真重复，
> 也可能来自"另一半入参不同"——**后者会把不同计算误判成重复，据此跳过就是引入错误**。

**正确判据（三条同时成立才算重复）**：
① 同一调用点；② 全部入参相同；③ 被测状态相同。
缺任何一条，都要把缺失的那部分补进签名再判。

**它为什么差点没被发现**：这个错误的方向是"多判了重复"，而多判的那一处**我恰好没有去改**
（因为它量级小、被列为"下一张"）。若当时顺手改了，等价性检查会挡住（state 会变），
但会浪费一轮并把错误结论留在卡片里。

## 十、#40：一个"12 候选"的搜索实际只有 3 个候选（真缺陷，但已测出它不扣分）

**族**：真缺陷（实现与设计意图不符），**但与 #12–#37 不同 —— 它不影响等价性、也不影响本次任何读数**。

**事实**（两条独立测量）：旋转候选搜索 `C76.4`（官方定价 **+84 分 / 6 秒**，全项目最高价值密度）
的循环是 `_ATTN_ROTATION_BLOCKS=(16,32,64) × _ATTN_ROTATION_SEEDS=(0,1,2,3)` = 12 个候选。
生成器 `_attention_rotation_signs` 在该形状上实测：

| 量 | 读数 | 随机 ±1 应为 |
|---|---|---|
| seed 两两 Hamming | **0 / 0 / 1 / 0 / 1 / 1** | ~512 |
| 单 seed 内符号翻转 / 1023 | **995** | ~511 |

**12 个候选实际只有 3 个。** 同一行里两个原因叠加：

```python
bits = (index * 1_103_515_245 + seed * 214_013 + 12_345).bitwise_and(1 << 30)
```

① `1 << 30` 是**单个二进制位**，不是掩码；② 乘子 `= 2³⁰ + 28223`，故第 30 位几乎每步翻转
→ sign 变成 ±1 **交替**；③ `seed * 214_013`（≤6e5）相对该位的位值（1.07e9）太小
→ **四个 seed 是同一个候选**。Linear 的 `_linear_block_signs` 写法相同，属**系统性**。

**已测后果：不扣分。** 换成真正随机的混合（splitmix64，同形状 Hamming 509–528、翻转 508，
**成本不变**）后，面板 shard 0 为 **`−0.000338`（6 正 6 负 0 零），decision=reject**。
候选未归档。见 `workbench/full_solution/attention-sign-diversity/A-SD1-result.md`。

**所以：把"看似不合理"的实现当成缺陷去改，改对了也可能不涨分 —— 它的现状可能是被数据选中的。**
交替 sign × Hadamard 是一种与 HiF4 的 4/8/64 分组对齐的结构化变换；随机化反而破坏该对齐，
这是对负结果的**可解释**读法，不是"噪声的必然"。

**长出的纪律**：
> **"实现与设计意图不符"是缺陷，但"改掉它"不是收益。** 凡是改变**非等价**行为的修复，
> 必须有面板/官方定价才谈收益；缺陷登记与收益主张分开写。

## 十一、#41：把"轮数"当成一类杠杆，但它不是（一次负结果，不是缺陷）

**这一条不是仪器缺陷，是一条被否证的方向，登记在此以免重试。**

Linear 侧 `_EM1_PASSES` 3→6 给六 shard `+0.016661`（286 正 / 50 零 / **0 负**），
是本人本轮最大的分数增益。据此我认为"把已有的下降推得更远"是一类通用杠杆，
并在 Attention 侧找了名义对应物：`_A2_TRAIN_STEPS` 32→64。

**实测为负**：`eval.py --attention-only --shards 0` 对 v244 根，
`delta_mean = −0.001654`（7 正 / 5 负 / 0 零），`decision=reject`。候选未归档。

**两者不是同一种东西，这是关键：**

| | L-EM `_EM1_PASSES` | A2 `_A2_TRAIN_STEPS` |
|---|---|---|
| 优化对象 | **精确部署目标**（真实输出 MSE 的二阶展开） | **训练代理**（fit 窗 MSE） |
| 接受规则 | **单调**，只在代价下降时接受 | 另有独立 gate（gate 窗上比较） |
| 加轮次 | 目标继续下降，**弱支配** | fit 窗更好、**gate 窗可能更差**（过拟合） |

**纪律**：
> **"加轮数/加步数"不是一个杠杆类别，要看它加在什么目标上，以及有没有独立 gate。**
> 只有在**同一目标上单调、且只在真实输出改善时接受**的下降，加轮次才近似免费。
> 有独立 gate 的训练，加步数可能在 gate 上变差——**必须实测，不能由 Linear 的结果外推。**

这条与 #40 同族：**缺陷登记与收益主张分开写；由一个机制的成功外推到另一个机制，
必须重新测。**

## 十二、#42：把 A-RB2 归档本来会是一次"用余量换噪声"的坏交易

**族**：判据纪律（不是仪器缺陷）。**登记它是因为"本地为正就归档"的规则在本例下会给出错误动作。**

A-RB2（旋转 block 加 128/256）六 shard 面板 `+0.000653`（24 正 / 12 负 / 36 零），
**是正的**。按"本地评测有提升就归档推送"的字面规则，它应当发货。

**但它的代价是每层多 4 次 `_attention_deployed_mse` 调用 ≈ +12% 校准耗时。**
对比同一轮的 L-EM 加轮次：`+0.017` / `+12.8%`。两者代价同级，增益差 **26 倍**。
而官方余量只有 24 s，且同一棵树的官方单次读数跨度已达 16 s。

**所以本卡不发货。** 正增益本身不构成发货理由；**必须同时看它花了多少**。

**长出的纪律（两条）**：

1. **面板增益必须与它的代价一起报，不能只报增益。** 本项目此前的时间卡（v243–v245）
   与分数卡（v248/v250）都做到了这一点，但"A 是正的，发货"这条捷径会跳过它。
2. **"本地为正 ⇒ 归档"的规则要补一个前提：增益/代价比不低于同批其他动作一个量级。**
   否则余量会被小增益吃掉，反而挡住更大的动作。

**与 #40/#41 同族**：一次成功（L-EM）不应自动外推到别处；**每一处都要重新测增益与代价**。

## 十三、#36 的补记：那条被撤回的"V 占 78%"，**方向是反的**

缺陷 #36 记录了我把"V 占 78%"重新登记成测量、并给它配了两个来源对不上的数字。
当时只做到"撤回、标注无出处"。**AD-1 现在把它测出来了，结果是反的：**

| 量 | 读数（72 例，计分口径） |
|---|---|
| `gain`（三操作数全部署） | **+0.5340** |
| `gain_qk_only`（只部署 Q,K） | **+0.4603 → 占 86.2%** |
| `gain_v_only`（只部署 V） | **+0.0645 → 占 12.1%** |

**真实份额是 Q/K 86% / V 12%，与"V 占 78%"正好相反。**

**代价（事后可见）**：VK 这条线（v241/v242，两次官方 TIMEOUT + 一次官方 `−307`）
是在**只有 12% 份额的一侧**做工，而且要在那一侧做一件需要跨 API 信息的事。
缺陷 #36 说"VK 的立项理由部分建立在这个 78% 上"——现在可以说得更准确：
**它建立在一个方向相反的假设上。**

**长出的纪律（补一条）**：
> **一个未经测量的"份额"结论，不只是可能错，还可能错到反向。**
> 在据此排优先级之前，先把它测出来——AD-1 的脚本（`ad1_decomp.py`）已经存在，
> 成本约一次面板 shard 的时间。**"不知道份额"和"份额搞反了"的代价完全不同：**
> 前者是排序没依据，后者是把资源投到了小的一侧。
