## 2. L-QF1：修正局部二次代价（首卡）

假设：当前候选排序使用了错误的局部二次代价，正确二次型能减少误提议与漏选；是否最终增益必须实测。

- 入口：`_em1_dynamic_descent` 的 `quadratic` 计算；当前式 `krba,bij,krbj->krb`。
- 唯一改动：改为 `krbi,bij,krbj->krb`，实现 `delta^T local_gram delta`。暂不改成特化对角公式、不换计算库、不改其他路径。
- 固定：继承父K（当前1）、8个pm1候选、16组调度、覆盖范围、scale/hierarchy/sign语义及整行联合接受全部不动。
- 工作目录：`workbench/full_solution/linear-qf1-quadratic-cost/`，完整候选自包含；根和既有归档只读。
- 最小验证：非对角SPD矩阵与单坐标/一般delta的显式二次型对照；验证线性项+二次项与直接目标差一致；包含旧式不等于真值的反例。用独立参考式，不写自我重复测试。
- 验证六API独立导入、合法state、finite、Attention/Weight控制、真实提议及最终接受计数、硬码变化；关闭修正时复现父。

### 4.1 定位已完成：拆分实测，分支 2 被推翻

上表的 90–93% 是"关掉 `em1` 载荷后的整段"，它同时包含 nvfp4 编码/舍入、GPTQ 的逐块 solve、
块序选择、以及 hook 与 state 拷贝。把它直接当成"逐块 solve"就是拿猜测当定位，
所以本卡先补了**一个**探针（`workbench/full_solution/linear-parent-path-split/split_probe.py`，
RTX 3060 Ti、CUDA event、同 state 同设备、无 profiler、15 轮取中位、事件与 `perf_counter` 双钟）。
探针按名解析父根自己的助手并在模块全局上包一层直通 wrapper——发布代码一个字节未改。

**外层拆分（CUDA event 中位；比例为占整次调用的百分比）：**

| 部件 | layer0/q 2560ch,128行 | q,512行 | layer0/o 4096ch,128行 | o,512行 |
|---|---:|---:|---:|---:|
| 整调用 `full_ms` | 539.81 | 899.03 | 498.53 | 530.23 |
| `dense`（nvfp4 解码 + smooth + permute） | 0.14% | 0.09% | 0.16% | 0.18% |
| `order`（块序选择） | 0.04% | 0.03% | 0.05% | 0.05% |
| `gptq`（`_combined_dynamic_fast_reordered_gptq`） | **93.4%** | **94.7%** | **86.0%** | **80.1%** |
| 残差（hook + state 拷贝 + CPU 空隙，含 L-EM2 下降） | 6.45% | 5.21% | 13.75% | 19.65% |

**内层拆分（在 gptq 内；两列分别为占 gptq 与占整次调用）：**

| 部件 | q,128行 | q,512行 | o,128行 | o,512行 |
|---|---:|---:|---:|---:|
| `encoder`（`_dense_to_hif4`，每次调用 40/64 次） | **93.6% / 87.4%** | **96.0% / 90.8%** | **87.4% / 75.2%** | **87.1% / 69.8%** |
| `solve`（`torch.linalg.solve`，39/63 次 = 块数 − 1） | 2.55% / 2.38% | 1.57% / 1.48% | 5.09% / 4.38% | 4.95% / 3.97% |

调用次数自我印证：`encoder` 40/64 次正是 2560/64 与 4096/64 的块数，
`solve` 39/63 次正是块数 − 1，即补偿只在该处发生，没有跑到别的路径上去。

**结论：分支 2 被实测排除。** 块间补偿系数全部加起来最多占一次调用的 **2.4–4.4%**
（`solve` 中位占比），把它预计算到校准期，上限就是把这点拿掉——不是本卡要的"秒级"。
主项是**编码器 `_dense_to_hif4`**，占一次调用 **69.8–90.8%**，且它按 64 通道块被调用 40/64 次。

**一个额外的实测事实（决定了下一步怎么做）：编码器成本与行数几乎无关。**
4096 通道下，128 行 374.86 ms、512 行 370.05 ms（4 倍行数，成本不变），
每块 5.86 ms 对 5.78 ms；2560 通道下每块 11.80 ms（128 行）对 20.42 ms（512 行），
按行数线性拟合得**每块固定项 ≈ 8.93 ms + 0.0224 ms/行**，即 128 行时 76% 的每块成本与行数无关。
也就是说这一段的成本主要是**逐块固定开销**，不是逐行算术——与"每块一次候选 scale 精确求解"
的结构一致（`refine_cap` 被 `max_refine_blocks` 夹住，与行数无关）。

### 4.2 定位第二层：编码器内部，成本是算子数不是浮点

`encoder_probe.py`（同一目录）回答 §4.2 上一版留下的问题。每编码器调用（父根 layer0，CUDA event 中位）：

| | q 2560ch/128行 | q/512行 | o 4096ch/128行 | o/512行 |
|---|---:|---:|---:|---:|
| 编码器 total | 12.750 ms | 20.911 ms | 5.956 ms | 6.087 ms |
| 候选精确解·批量 `[6,N,8,2,4]` | 3.360 (26.4%) | 11.124 (53.2%) | 0.869 (14.6%) | 0.886 (14.6%) |
| 候选精确解·边扩展（4 维、逐步） | 4.602 (36.1%) | 4.636 (22.2%) | 1.253 (21.0%) | 1.290 (21.2%) |
| `_adaround_mantissa` 直接调用 | 0.711 (5.6%) | 1.548 (7.4%) | 0 | 0 |
| 其余（前导张量搬运） | 4.077 (32.0%) | 3.603 (17.2%) | 3.834 (64.4%) | 3.911 (64.2%) |

三条与分支选择直接相关的读数：

1. **候选数 K=6**（`_offsets_as_tuple` 前置 `0`），且 `max_refine_ratio≈0.99`、`error_threshold=1e-7`
   使几乎每行都进 refine（q/512 的 N=509=`ceil(512×0.99366)`）：refine 不是挑选。
2. **aten 算子数只随配置变、不随行数变**：o 两个行数下都是 425 个/调用（逐项相同），
   q 是 1060 与 1068。折算 µs/算子：q/128 11.8、q/512 19.6、o 两个行数都是 14.0。
   这就是"每块成本与行数无关"的机制——**成本 = 算子数 × 每算子固定代价**；q 涨的那部分是数据量驱动
   （16 倍展开的中间张量），o 完全由算子数决定。主线程 CPU 时间占墙钟 94–100%，即整窗口都在 CPU 侧付费。
3. **两类层的热点不同**：有 gram 的层（2560 通道）走 `_adaround_mantissa` 的 16 模式枚举，
   占编码器 51%（128 行）到 68%（512 行）；无 gram 的层（4096）根本不调它，前导搬运独占 64%。
   父根 168 个动态调用点里 2560-gram 有 120 个、4096-no-gram 24 个、9216 24 个（且后者不在 metric 作用域）；
   **gram 层约占动态激活宽度的 76%**，所以本卡取 gram 层那条热点。

### 4.3 固定卡：分支 3，去掉 16 模式枚举里的整数物化

- **唯一改动**：`_adaround_mantissa` 里"`floor`/`ceil` → `.to(torch.int64)` → `torch.where` 张成 16 倍 →
  `.to(torch.float32)` → `*0.25`"这条链，改为先在 `[K,N,8,2,4]` 上算出 float 的
  `floor_m = floor(raw).clamp(0,6)*0.25` 与 `ceil_m = ceil(raw).clamp(0,7)*0.25`，再做一次 float 的
  `torch.where(mask, ceil_m, floor_m)`；并把只依赖常量（与输入无关）的 `masks` 提到调用外。
  **16 模式候选一个不减，选中的模式、loss、argmin、gather 全不变。**
- **为什么是逐位等价而不是近似**：`floor/ceil` 的结果是整数，`clamp` 界是整数，整数乘 `0.25` 在 fp32 上
  精确可表示，`where` 的选取集合相同，后面的 `all_delta`、einsum、`argmin`、`gather` 输入逐位相同。
  收益来自把 16 倍中间张量从 int64（8 字节）降为 float32（4 字节）并去掉三次 dtype 转换。
- **保持不动**：编码目标、候选集合（offset 与 source proposal 一个不减）、覆盖范围、舍入候选、
  refinement 轮数、`refine_cap` 语义、接受判据。**不减少任何候选换时间。**
- **不碰**：补偿系数（实测 ≤4.4%）、块序选择（≤0.05%）、dense 构造（≤0.18%）、
  边扩展的轮数与方向、Attention 半边、权重侧机制、本计划前两卡的机制。
- **共享助手的硬线**：`_adaround_mantissa` 同时被权重/静态路径调用（`_solve_exact_hierarchy` 3513、
  `_dense_to_hif4` 3780，而 `_solve_exact_hierarchy` 另有 1475/1970/7222/7258/7427/7463 等调用者），
  所以等价性必须**对全部调用者**证明，不能只说"激活路径没变"。
  五字段硬码逐位相同是接受线，不是容差线（`numpy().tobytes()` 比较，不用 `torch.equal`）。
- **门**：官方硬限 300 s，父根 292 s。以"官方秒数可分辨地下降"为唯一接受条件；
  精度侧六 shard 同口径，回退逐条记录。计时用同 state 同设备、独立无 profiler 配对，并带同字节 sham 对照。
