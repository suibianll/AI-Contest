## 机制：父根把同一个梯度算了两遍，第一遍的结果被丢掉

`_em1_dynamic_descent` 在进入 pass 循环之前先算一次梯度，**只为做有限性检查**：

```python
gradient = (deployed - reference).mm(metric) + reference.mm(h_matrix)
if not torch.isfinite(gradient).all():
    ...  # 走 nonfinite-gradient 分支
    return
```

然后循环体第一句**又算一遍同样的表达式**，把那个名字重新绑定：

```python
for _pass in range(_EM1_PASSES):
    gradient = (deployed - reference).mm(metric) + reference.mm(h_matrix)   # 父根
```

`_EM1_PASSES = 1`（`solution.py:11941`），所以每次调用这两遍都跑，而第一遍的结果除了被判一下有限性以外没有别的用途——**判完之后就被覆盖了**。

候选把循环里那一遍收进 `if _pass:`：

```python
for _pass in range(_EM1_PASSES):
    if _pass:
        gradient = (deployed - reference).mm(metric) + reference.mm(h_matrix)
        if not torch.isfinite(gradient).all():
            aborted = True
            break
```

pass 0 复用父根刚算过、刚检查过的那一份；pass 1 及以后**照旧重算**。

### 为什么不是"提出循环"，以及为什么这不影响 pass ≥ 1

pass 体里有原地写：

```python
deployed.add_(row_delta.mul_(keep_scale))
gradient.add_(g_delta.mul_(keep_scale))
```

梯度赖以计算的两个张量在 pass 0 之后就不存在了。把整个表达式提到循环外会让**每一个**后续 pass 用错的值；`if _pass:` 而不是"提出来"正是为此。这是机制成立的前提，不是实现细节，所以静态（`premise.py`，判据 P4）和动态（`verify.py` 的 E2、F）各测了一遍。

### 两遍的结果为什么必然相同

同一表达式、同一批张量。`premise.py` 静态走查两点之间所有语句：对被观察名字的重新绑定**有且仅有一次**——`deployed = deployed.clone()`，逐元素保持原值；`deployed` 和 `reference` 没有原地写。`verify.py` 的控件 C 在运行时复核：两遍各自的两个 `mm` 乘积**逐位相同**（合成层与真实 layer0/q 均如此，product 0/1 都 True）。

## 候选构建：改动由机器测量，且是 AST 级相等

`build.py` 不手写覆盖函数，而是从父根字节里切出 `_em1_dynamic_descent` 的源码、替换一个子串、追加回去。

**这张卡不报"逐字节差异数"。** 改动是**插入一行**，插入点之后所有字节整体位移，逐位置比较会把整条尾巴都报成"不同"——那是个看着像证据、其实不是数字的数。改报两个有意义的量：

- `substitutions_performed = 1`（未加保护的循环头出现 1 次、已加保护的 0 次，否则拒绝构建）
- `extracted_function_changed_lines = 5`，`byte_delta = 34`
- **`ast_identical_after_dissolving_pass_guard = true`**：把插入的那个 `if _pass:` 节点溶回父块之后，两棵 AST 的 `ast.dump` **完全相等**。这比字节计数更强——执行的语句树除了那个保护以外一个节点没变。这个等式由 `verify.py` 控件 A **独立重算**，归档不建立在构建脚本的自述之上。

`_em1_dynamic_descent` 由父根 hook 在调用时从模块全局解析（`co_names` 含该名字），所以追加定义遮蔽父定义，父根两个 hook 一行未碰。候选里唯一的变化是"父定义变成死代码"。

## 算子账：少两个矩阵乘，且只有两个

`verify.py` 控件 D 把 `torch.Tensor.mm` 包起来，记录双方**完整的**乘积序列。K=1：

- 父根 **20** 个乘积（循环前 2 个 + 一次 pass 的 2 个梯度 + 16 个步进）
- 候选 **18** 个
- 候选的**形状序列 = 父根的序列删掉第 2、3 个**，其余一字不差；合成层与真实 layer0/q 都对得上

去掉的就是 pass 0 那遍梯度的两个乘积，`2 × 2 × rows × channels²` FLOP：128 行是 3.36 GFLOP，512 行是 13.4 GFLOP。

**控件 E2 是这次验证里最关键的负向对照**：把 K 在内存里改成 2，并给 pass 1 的梯度在父根会走到的那个 `mm` 上投毒成 NaN。父根发 **22** 个乘积、在第 21 个中止；候选发 **20** 个、在第 19 个中止——偏移正好是那 2 个——**两者的输出逐位相同**。两个都停在第二个 pass 的任何步进之前，说明保护没有把重算提出循环：K ≥ 2 时后续 pass 照样重算、照样在父根停的地方停。

### 这次官方读数量出的、本地量不出的东西

336 个配对 case **全部精确零**，0 正 0 负；机制被证明恰好删掉每次调用 2 个矩阵乘、别无其他；
它的墙钟值低于本机所有时钟的分辨力，这一点带 null 对照记录在案而不是绕开。

**官方机把它量成了 −4s。** 本地测量读不出，不等于收益是零——本机时钟的分辨力就是极限，
而官方机（CPU 侧固定开销主导）把每次调用的两个矩阵乘累积成了秒级差值。这条**修正本卡归档时
"应当成本相同、期望略低"的措辞**：方向是对的，量级不是"略"，而是本机可测量的下界之下、
官方可测量之上。

这也是本仓库第一次把一个**本地不可分辨的等输出提速候选**用一次官方验证定价（AGENTS §2
"不同执行成本的等输出实现可作一次正式提速验证"的首个正向实例）；此前同类判断只有 v202 的
+8s，而 v202 的输出也是逐位等价的。

本地工具的 `no_effect` 是它自己 `delta_mean > 0 and L1 < 0.02` 的**小趋势筛选门**——对一个按构造
输出等价的候选报 `no_effect` 是**设计中的结果**，不是被拒。归档照录工具原判，不重述。

### 未兑现的部分：L-TF1 还没上当前根

本卡测的是 **v230 根上的 L-TF1**（K=1）。当前根 v231 是 K=2，而该保护删掉的只是**被重复计算的
pass 0 那一次**——K=2 投毒对照已经证明偏移在 K=2 下仍是 2 个矩阵乘。因此"把 L-TF1 移植到 v231"
是把这次官方定价的 −4s 应用到当前根上的自然候选。**不给官方秒数预测**；新候选须独立构建、
独立提交、由官方数字裁决。

**血统**：v233 是 v230 的后代，**不含** v231 的 K=2 机制、也**不含** v232 的 L-QF1 二次代价修正；
它是父根加一行保护。三个候选是**兄弟不是叠加**，本地 Δ 不可相加、也不可当序列读。Attention
半边与父根完全一致（v195）。
